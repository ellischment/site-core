# CLAUDE.md: правила работы над основой

Этот файл агент читает при каждом запуске. Не удалять и не переименовывать.

## Что это

`site-core`: одна основа для клиентских сайтов (заявки, запись, каталог, отзывы, блог, галерея, админка, SEO, выкладка на дешёвый сервер). Каждый клиент получает копию основы и отличается только конфигурацией, темой, текстами и набором включённых модулей.

Источник кода: `../prince-u-lis` (сайт «Принц и Лис»). Его только читаем, ничего в нём не меняем.

## Порядок работы

В начале задачи:
1. Прочитать этот файл и `STATE.md`.
2. Для задач с модулями, кэшем, админкой прочитать `docs/core-map.md`.
3. Проверить `git status`: незакоммиченное разобрать до начала работы.

В конце задачи:
1. `npm run check` зелёный. С красной проверкой задача не закрыта.
2. `STATE.md` обновлён: только текущее состояние и открытые вопросы.
3. Коммит с понятным сообщением на русском. Один логический шаг, один коммит.

## Правила кода

- **Никаких значений конкретного клиента в коде ядра и компонентов.** Название, цвета, шрифты, контакты, домены, тексты берутся только из `client.config.ts`, `theme/` и базы (`SiteText`). Это проверяет тест `tests/no-client-values.test.ts`.
- **Различия клиентов решаются конфигурацией или модулем**, а не правкой ядра. Пришлось править ядро под клиента: это дыра в конфигурации, её надо закрыть.
- **Версии Next, React, Prisma** как в `../prince-u-lis/package.json`. Мажорные версии не поднимать без согласия владельца основы.
- TypeScript строгий, `any` запрещён.
- Серверная валидация обязательна для всех форм (zod). Клиентская не заменяет серверную.
- Любой обработчик формы пишет в базу до обращения к внешним сервисам. Падение внешнего сервиса не роняет заявку.
- Любое серверное действие панели идёт через `panelAction` (`lib/action.ts`): роль, схема, транзакция, журнал, сброс кэша.
- Проверка роли на сервере в каждом действии и разделе, а не скрытием пунктов меню.
- Сырой SQL запрещён, кроме `PRAGMA` при инициализации.
- Секреты только в переменных окружения. `.env` в git не попадает.
- Цвет в `app/` и `components/` только через `var(--*)`. Сырой hex и rgb живут в `theme/`.
- Заглушка загрузки (`loading.tsx`) только в сегментах, ниже которых никто не зовёт `notFound()` или `forbidden()`: иначе 404 и 403 превращаются в 200.

## Правила тестов

- **Новый тест обязан «кусаться»:** вернуть баг и увидеть красный тест.
- **Тест импортирует константы**, а не копирует значения.
- **Тест создал данные, тест их и удалил.** Если тесту нужны данные, он заводит их сам.
- Красная проверка чинится в тот же день.
- Ключи интеграций в сквозных тестах обнулены: тест не должен слать уведомления в боевой чат.

## Персональные данные (152-ФЗ)

У каждого поля с персональными данными записано: зачем и на сколько хранится. Таблица в `docs/personal-data.md`. Поле без ответа «на сколько» уже проблема. Имя и телефон в базе шифруются (`lib/crypto.ts`), в журналах только маска.

## Тексты

Документы и тексты интерфейса на русском. Без длинного тире, короткие предложения.

## Единственные источники правды

Если два файла говорят разное, побеждает источник из таблицы. Расхождение это ошибка, о ней надо сказать.

| Что | Где |
|---|---|
| Данные клиента: название, реквизиты, контакты, домены, модули, меню, SEO | `client.config.ts` |
| Цвета, радиусы, тени, отступы, шрифты | `theme/tokens.ts`, `theme/fonts/` |
| Тексты, которые правит владелец | таблица `SiteText` в базе, значения по умолчанию в `lib/site-texts.ts` |
| Модель данных | `prisma/schema/*.prisma` (ядро в `core.prisma`, модули в своих файлах) |
| Разделы админки | реестр `lib/admin-sections.ts` |
| Теги кэша и карта сброса | `lib/cache.ts` |
| Описание модуля: зависимости, настройки, теги, cron | `modules/<id>/module.ts` |
| Персональные данные: зачем и на сколько | `docs/personal-data.md` |
| Текущее состояние и открытые вопросы | `STATE.md` |
| Выкладка и сервер | `DEPLOY.md`, `scripts/` |

## Чего не делать без спроса

- Поднимать мажорные версии зависимостей.
- Добавлять библиотеки без записи причины в `STATE.md`.
- Делать «заодно» рефакторинг соседнего кода.
- Переносить в ядро то, что нужно одному клиенту.
